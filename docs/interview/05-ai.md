# 5. The AI components

Three pieces: an LSTM price predictor, news sentiment scoring, and a chat agent.
Two of the three have measured evaluations, and **both evaluations came back
negative**. That is the most valuable material in this project — handle it as a
strength, not an embarrassment.

## Price prediction (LSTM)

Features: `log_ret`, `volume_log`, `sentiment`, `rsi`, `macd`, `bb_width`. A
24-candle window predicts the next candle's log return, which is then turned into
a BUY/SELL/HOLD signal. Trained in a notebook on Colab, served as TorchScript.

### What the evaluation found

Measured on the notebook's own chronological split — 4,995 BTCUSDT 1h test bars:

| Model | RMSE (log-ret) | Directional accuracy |
|---|---|---|
| Naive (predict zero) | 0.005874 | — |
| Majority class | — | **50.9%** |
| Persistence | 0.008396 | 48.0% |
| **LSTM** | 0.005883 | **49.1%** |

**The model has no directional edge.** It calls direction correctly 49.1% of the
time against a 50.9% floor, and its RMSE is very slightly *worse* than predicting
no change at all.

The harness first reproduced the notebook's stored test RMSE of 367.95 USD to
0.0000 difference, which is what makes the rest of the table trustworthy: it is
measuring the same bars the notebook did.

**Why low RMSE is not a defence.** Log returns are tiny and centred near zero, so
a model that always predicts ≈0 scores a good RMSE while being useless. That is
exactly what happened. Directional accuracy is the metric the trading signal
actually depends on, which is why the harness reports both.

### The train/serve bug it surfaced

`bb_width` reaches the model on a different scale in production than in training:

- Training used a percentage: `4.269930`
- Serving computed a fraction: `0.042699`
- Ratio: **100.0x**

The model receives a feature a hundred times smaller than anything it saw in
training. A unit test now pins both values so the discrepancy cannot be quietly
"fixed" on one side without the test failing.

This is a good story to tell: it is a class of bug — training/serving skew — that
no amount of model work would ever surface, and only appeared because someone
rebuilt the feature pipeline from scratch to check.

## Sentiment analysis

Two interchangeable backends behind one API, chosen with `SENTIMENT_BACKEND`:

- **`gemini`** *(default)* — the API classifies each article into one of six
  emotions and assigns a score in `[-1, +1]`.
- **`local`** — a RoBERTa encoder on CPU. `LOCAL_MODEL_VARIANT` picks `base` (the
  public financial-sentiment checkpoint, untouched) or `student` (that checkpoint
  plus a LoRA adapter trained here).

Every stored document records which backend produced it. That came from a real
problem: the original code caught every exception and silently returned mock
output, so a dead API key, a rate limit and a healthy pipeline looked identical
from the outside.

### The fine-tune, and why it is a negative result

`train_distill.py` trains a LoRA adapter — rank 16, alpha 32, targeting `query`
and `value` — over `mrm8488/distilroberta-finetuned-financial-news-sentiment-analysis`,
with two heads trained jointly: MSE on the score, CrossEntropy on the emotion.
**300,295 trainable parameters, 0.36% of 82M.**

All three systems scored the same 50 hand-labelled articles:

| | `base` (no training) | `student` (LoRA) | API path |
|---|---|---|---|
| Bucket accuracy | **66.0%** | 58.0% | 56.0% |
| Emotion accuracy | n/a (3-class) | 28.0% | 24.0% |
| Latency / article | ~41 ms | 41 ms | 229 ms |
| Marginal cost / 1k | $0 | $0 | ~1350 input tokens each |

Majority-class floor: 36.0%. None of the 50 evaluation articles appear in the 140
training or 36 validation rows — the eval set was carved out before training data
was exported.

**The fine-tune cost 8 points against the checkpoint it started from.** Training
made a working model worse.

**The cause is label provenance, not method.** The API key was suspended before
the training set was exported, so the 176 rows carry labels from the keyword
fallback rather than from the model they were meant to distil. The student
learned to imitate a regex. Restoring the key and re-running the chain is what
turns this into a real distillation result, and the bar it must then clear is
66.0%.

**The conclusion that was acted on:** neither local variant was wired into
production, because shipping a model measurably worse than what it replaces is
not an improvement. The one legitimate finding is that the *untrained* public
checkpoint beats the paid API on this data — 66% vs 56%, 5.6x faster, no marginal
cost.

## The chat agent

`chat-agent-service` answers market questions from live system state rather than
model memory. Three tools:

| Tool | Backed by |
|---|---|
| `get_prediction(symbol)` | `prediction-service` |
| `get_sentiment_summary(symbol, days?)` | `sentiment-service` |
| `search_news(query, symbol?)` | Qdrant top-k over `news_chunks` |

A Gemini function-calling loop, capped at three tool rounds. Tools within a round
run concurrently via `asyncio.gather`. The answer streams over SSE in the format
the frontend already parsed, so the chat panel needed no changes.

Three design decisions worth explaining:

- **Tools never raise.** Every failure returns `{"error": ...}` so the model can
  say "I couldn't get that". A degraded answer beats a 500.
- **Results are trimmed before reaching the model** — colour codes and emoji
  stripped, a raw sentiment float bucketed into a word, because a bare number
  means little to an LLM.
- **Every turn emits a trace** — which tools ran, with what arguments, how long
  each took — so "did it actually retrieve anything?" is answerable with `curl`
  instead of trust.

`AGENT_BACKEND=rules` is a deterministic keyword planner over the same tools,
used as the fallback whenever Gemini fails. It drives the identical execution
path, and its output states plainly that no model wrote it.

**What has never run:** the Gemini loop itself, because the key is suspended.
Tool execution, tracing, retrieval and streaming are all exercised; the model call
at the top is not. Say this if asked — it is the honest boundary of the demo.
