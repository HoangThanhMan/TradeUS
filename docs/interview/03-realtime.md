# 3. The real-time tier

The part of the system most worth talking about in a backend interview, because
it is the part with measured numbers behind it.

## Path of one price update

```
Binance futures WS  →  collector-price  →  RabbitMQ  →  ws-gateway-N  →  browser
   (fstream)            routing key         topic       Socket.IO room    Socket.IO
                      price.<symbol>       exchange
```

`collector-price` subscribes to five symbols — BTC, ETH, BNB, SOL, XRP — on
`wss://fstream.binance.com/stream`, and republishes each update with routing key
`price.<symbol>`.

Each gateway consumes from its own queue and re-emits into Socket.IO **rooms**.
The room key is symbol plus interval (`BTCUSDT:1m`), so a client watching one
chart receives only that stream, not all five symbols. A client can also join an
`all` room. On subscribe, the gateway first fetches 500 historical candles from
Binance REST and sends them, so the chart is populated before the first live tick
arrives.

## Load balancing, and why `ip_hash`

Nginx balances the Socket.IO path across the two gateways with `ip_hash`.

The reason is **state**: each gateway keeps its clients' subscriptions in memory
(`clientSubscriptions`, and the Socket.IO room membership). A client whose
connection landed on gateway 1 must keep reaching gateway 1, or its subscriptions
are gone. `ip_hash` pins by source address and achieves that without any shared
session store.

**Know the cost, because this is the follow-up question.** `ip_hash` distributes
by IP, not by load, so many users behind one NAT all land on one gateway. The
principled fix is to make gateways stateless — move subscription state into Redis
and add the Socket.IO Redis adapter — after which any balancing policy works and
a gateway can die without dropping its clients' subscriptions. That was not built;
say so plainly and describe it as the next step.

## Rate and connection limits

The Socket.IO location carries per-IP protection:

```nginx
limit_req  zone=ws_limit burst=20 nodelay;   # 10 new requests/sec per IP
limit_conn ws_conn 50;                       # 50 concurrent connections per IP
```

This is genuinely enforced — an early load test opened 50 connections at once
from one address and every one was rejected until the client ramped instead. Worth
mentioning as an example of a limit that did its job on the person who wrote it.

## Measured performance

Run on a 7 GB laptop, no GPU, all containers on one host. Load generated by a
Node script driving `socket.io-client`, each client subscribing to all five
symbols at the `1m` interval.

### Through the load balancer

| | |
|---|---|
| Clients | 50, ramped at 8/s (to stay under `limit_req`) |
| Connected / failed | 50 / 0 |
| Throughput | 52.8 msg/s |
| Latency | p50 2 ms, p95 4 ms, p99 5 ms |
| Gateway distribution | 100% to `ws-gateway-2` |

The single-gateway distribution is `ip_hash` behaving correctly: one source IP,
one gateway.

### Direct to both gateways

Bypassing the per-IP limit — which in production applies per real user address —
to measure gateway capacity:

| Clients | Throughput | p50 | p95 | p99 | Failed |
|---|---|---|---|---|---|
| 400 (200 per gateway) | 466 msg/s | 3 ms | 6 ms | 8 ms | 0 |
| **1,000 (500 per gateway)** | **1,154 msg/s** | **5 ms** | **10 ms** | **13 ms** | **0** |

Broker at that load: **6 queues, 8 consumers, backlog 0**. Nothing accumulated,
so the consumers were keeping pace with the producer.

### What the latency figure actually measures

Gateway emit → client receipt. The message payload carries `timestamp: Date.now()`
set by the gateway at emit time, so the measurement covers Socket.IO serialisation
and the network hop, **not** the full path from Binance.

End-to-end latency from the exchange is not measurable with the current payload,
because the collector does not forward Binance's event time. Say the smaller,
true thing. If asked how you would measure the real number: stamp the Binance
event time in the collector and carry it through, then the same harness reports
end-to-end.

### Reproducing it

```bash
docker compose -f docker-compose.dev.yml up -d rabbitmq redis mongodb \
  collector-price ws-gateway-1 ws-gateway-2 nginx
# broker rates
curl -s -u guest:guest http://localhost:15672/api/overview | jq .message_stats
# client load — the script lives in the session scratchpad, ~40 lines of
# socket.io-client opening N sockets and timing received frames
```

## Honest limits

- One host. This measures a single machine's capacity, not a distributed cluster.
- 1,000 clients is where it was *tested*, not where it broke. The ceiling is
  unknown; do not describe 1,000 as a maximum.
- Five symbols. Throughput scales with symbol count and would need re-measuring.
- No reconnection storm test. Socket.IO's automatic reconnect is enabled but the
  behaviour of a thousand clients reconnecting at once is untested.
